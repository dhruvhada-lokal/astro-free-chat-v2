# Prompt / config versions

Every change to `config/` bumps `experiment.prompt_version`. `/admin` shows each version separately.

| Version | Date | What changed |
|---|---|---|
| free_chat_v4.2 | 4 Nov 2026 | Reverted prompt_template.md and reply_instructions/insight_levels/question_budget/chart_line back to the exact free_chat_v2.6 content (recovered verbatim from Claude Code's file-history backups), per request — scoped to prompt content only. This restores the ask_yes/ask_no mechanism (only compatible with the old prompt — the new prompt's "no more questions" rule is what made it a contradiction) and removes pacing.post_kundli_gap_ms/post_kundli_typing_ms (built specifically for the new hook/doubt bubble structure). Everything independent of prompt wording from v2.7–v4.1 is KEPT: MAX_CLARIFY_ROUNDS=1, the gather-fallback topic preference and dedup, topics.parivaar's expanded keywords, the chartFactHit stacked_terms guard, the st.answered stuck-loop fix, fallback_reply_alt, topic_followup, and the llmWaitMs clock-drain fix (with llm_timeout_ms 18000 / max_output_tokens 500). See docs/changes-before-prompt-rewrite.md and docs/changes-after-prompt-rewrite.md for the full breakdown |
| free_chat_v4.1 | 4 Nov 2026 | The real fix for the timeout/clock tension (v3.8/v4.0 only traded one problem for the other): time spent waiting on a model call — success, retry, or eventual timeout — no longer drains the user's free_seconds. New SessionState.llmWaitMs tracks total wait time per session; secondsLeft() (src/lib/chat.ts) subtracts it from elapsed wall-clock time. This makes a generous llm_timeout_ms safe to use, so it's back to 18000 (covers most real gemini-3.5-flash-lite replies) without the chat hitting closing_at_seconds_left after 2-3 messages. max_output_tokens back to 500 too (reverted per request; benchmarking never showed it affecting latency either way) |
| free_chat_v4.0 | 4 Nov 2026 | llm_timeout_ms 18000 → 10000. A real chat showed the actual cost of v3.8's 18000: secondsLeft is pure wall-clock time with no awareness of server-side waits, so two failed calls alone burned ~36s out of the 120s budget, and the chat hit closing_at_seconds_left after just 2-3 messages. 10000 balances letting more real replies through against how much clock time a failure costs the user |
| free_chat_v3.9 | 4 Nov 2026 | model.max_output_tokens 500 → 200: a 2-3 bubble, ~30-50 word reply never needed 500 tokens of room. Benchmarking showed latency variance comes from Gemini's side, not prompt size or token budget, so this isn't a fix for the latency itself — a small, safe trim with no effect on output quality |
| free_chat_v3.8 | 4 Nov 2026 | llm_timeout_ms 6000 → 18000: real gemini-3.5-flash-lite latency has typically run 10-17s today, so 6s meant most turns discarded the real reply and sent the fallback instead — all of today's prompt work would rarely have been seen by a real user. The client already shows "typing…" for the whole wait (not just during reveal), so this needed no UI change. Fallback should now be the rare safety net it was designed to be |
| free_chat_v3.7 | 4 Nov 2026 | A gather-stage model failure right after a topic was named (e.g. "Promotion") fell back to topic_hook ("Naukri ke baare mein jaanna hai?") — a yes/no topic confirmation, not a real follow-up, which reads as if Omkar didn't actually listen. New scripted.topic_followup gives this fallback its own topic-specific clarifying questions ("Naukri mein abhi kya dikkat aa rahi hai?"), matching what the model itself is told to ask. Falls back to the old topicPromptLine behavior when the topic truly isn't known yet |
| free_chat_v3.6 | 4 Nov 2026 | Critical bug: a real chat got the exact same fallback_reply line 3 times in a row with no way out. Cause: unlike "gather"'s fallback (which advances clarifyRounds even on failure), a failed "answer"-stage call never set st.answered — so stageFor() kept forcing "answer" again every single turn, and every failure sent the identical line forever, with the conversation never progressing to "engage". Fixed: a failed "answer" call now sets st.answered = true so the chat always moves forward. Also added fallback_reply_alt (and a fallbackLine() helper) so if the generic fallback was already said once this chat, a second failure (in a different stage) swaps to a different line instead of repeating it too |
| free_chat_v3.5 | 4 Nov 2026 | Stacking two astrology terms in one bubble ("Shani aur Ketu ka asar", "Mangal ki mahadasha mein Budh ki antardasha") kept happening despite repeated prompt wording — the prompt alone wasn't foolproof. Added a code-level backstop: chartFactHit now counts every distinct planet actually named in a bubble and drops it (dropped:stacked_terms) if two or more appear together, regardless of phrasing. Also reinforced "same simplest everyday words as bubble 1" directly on the hook/doubt instructions themselves (answer, gather, engage, engage_doubt), not just the shared paragraph |
| free_chat_v3.4 | 4 Nov 2026 | When they push a second time right after the "need more details" redirect (e.g. "kya janna hoga", "bata do na"), engage no longer repeats that same line — it gives a fresh, different doubt-creating finding about their topic instead, varying each time they push, so it never feels like a stall. engage_doubt's own example was itself a generic line that could fit any chat ("Lekin iske liye aapko aage kuch cheezon ka khaas dhyaan rakhna hoga.") — now explicitly tied to their named topic, and never reuses a doubt already given. engage's main instruction now explicitly requires every reply to name their exact topic/situation, never a line generic enough to fit any chat |
| free_chat_v3.3 | 4 Nov 2026 | Bubble 1 (the finding) came out too complex and net-negative in a live test: "Mangal ki mahadasha mein Budh ki antardasha abhi mehnat ka pura fal nahi milne de rahi hai" stacks two astrology terms in one line and reads as a double-negative, discouraging statement — the opposite of "strongly positive". Redefined it as consoling-simple-positive: first a plain acknowledgment of what they're going through (in their own situation's words), then exactly ONE chart detail — a single dasha, antardasha or planet, never two stacked together — in one short, plain, present-continuous sentence, with no double negatives or convoluted phrasing |
| free_chat_v3.2 | 4 Nov 2026 | The indirect hook (bubble 2) was too generic ("Iske peeche ek baat aur chhupi hai" could fit any chat, any topic). It must now name THEIR exact situation (the interview, the rishta, the loan — in its own words) and frame the doubt as needing care about that specific thing ("dhyaan rakhna hoga" / "savdhan rehna hoga"), still never saying what it is or giving a timeframe |
| free_chat_v3.1 | 4 Nov 2026 | v3.0's output was still too literary for the target audience (saw "vichar", "gehra asar", and the model naming a rashi, which v2.6 had deliberately stopped the scripted chart line from doing — and which also risks the dropped:wrong_rashi guard eating a whole bubble). Added explicit do/don't vocabulary to the shared template and to answer/gather/engage ("vichar"→"sochna", "gehra asar"→"zyada asar", "nirnay"→"faisla") and banned naming the rashi/moon sign anywhere, not just in the scripted line. Dasha line simplified further ("Abhi aapki kundli mein X ki dasha..." → "Abhi X ki dasha chal rahi hai — yeh samay aapke liye accha ho sakta hai."). The indirect hook (bubble 2) must now never resolve or give a timeframe — previously "jald hi saaf ho jayega" type phrasing crept back toward a decisive prediction. New behaviour for when the hook actually hooks them and they ask a follow-up ("kya baat hai?" / "kab?" etc, in both "answer" push-back and "engage"): instead of giving a partial finding, Omkar now says — as a statement, never a question — that he'd need to understand their situation a little more, inviting them to share more rather than resolving the doubt |
| free_chat_v3.0 | 4 Nov 2026 | The kundli reveal now reads as one slow, hopeful moment: dasha line simplified and given a clearly positive spin ("Dasha X chal rahi hai" → "Abhi aapki kundli mein X ki dasha chal rahi hai — yeh samay aapke liye achha badlaav la sakta hai"; ta/te/ml dasha lines unchanged — same treatment needs native review before translating). Bubble 1 of the first finding is now explicitly "strongly positive, real hope" (still hedged, never a flat prediction); bubble 2 is redefined from a second positive line into an indirect hook — a soft, curious statement (never a question, never scary) that nudges them to keep talking, without naming what it is. New pacing.post_kundli_gap_ms/post_kundli_typing_ms (2500/2500 each): the dasha line, the finding and the hook now each get their own slow pause-then-typing reveal, instead of the normal length-based timing |
| free_chat_v2.9 | 4 Nov 2026 | Same symptom reported again ("Kis baare mein jaanna chahte hain aap?" twice) with a third cause: "bacche" (plural "children") wasn't in topics.parivaar's keyword list (only "bachche"/"baccha" were), so topic detection missed it and stage "gather" fell to its model call, which then failed and hit the same generic fallback line already sent by the earlier deterministic clarify_topic — and nothing stopped a fallback line from repeating a line already said. Added bacche/bachcha/bacha/santaan to topics.parivaar; and, more generally, the gather fallback now checks `previous` and swaps to the ordinary doubt-hook fallback_reply instead of repeating a line Omkar already said this chat |

Retired ask_yes/ask_no/the canAsk mechanism entirely (it actively told the model to ask a question, contradicting "no more questions after the one in gather"); question_budget 3 → 1, now purely a guardrail backstop so gather's one intentional question is never itself stripped |
